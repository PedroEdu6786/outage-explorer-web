- **D1: the app kept showing data after access was denied.** Imagine you open SQL results, then switch to Overview. The server tells the app, “You can’t access this data anymore.” Previously, the app cleared the page that received that denial, but the SQL results were still sitting in memory. Returning to SQL could show them again. A SQL request already in progress could also finish and put data back. **The fix:** a current denial now clears protected data throughout the app and blocks old requests from putting it back. You must click **Check session** before continuing. That checks your current access; it does not run SQL again. **D2: the app can confuse an old refresh with a new one.** Imagine: 1. Refresh A finishes successfully. 2. You start refresh B, but its response gets lost. B might still be running. 3. You click **Check refresh status**. 4. The app checks A instead and sees “finished.” Each refresh request has a unique key—think of it as a receipt number. Retrying with the same receipt lets the server recognize the original request instead of starting another refresh. The bug is that checking finished refresh A makes the app throw away B’s receipt. Your next retry could start another refresh instead of recovering B. **The planned fix:** track B’s receipt separately from A’s displayed result, and keep it until B’s outcome is resolved. **D1 is fixed and committed. D2 is still pending.**
